## 0. 核心命题（三句话）

1. **窗口是唯一排期依据** —— 一个任务**能不能现在跑**，只由它的**窗口集合**决定。
2. **队列顺序是唯一执行顺序依据** —— 谁先跑，只由 `run_list` 的**顺序本身**决定。
3. **"跑几次"由两件事表达** —— 任务内的**次数**（一轮打几场）与队列里的**重复条目**（跑几轮）。

★ 这三句合起来排除了所有"任务内自排期"（`custom_next_run`）、
"按间隔轮询"（`success_interval`）、"按存量补充"（`charge_*`）等历史机制。

★★ **S7 对命题 2 的强化**: 它是**唯一**的顺序权威 —— **没有**任何"模式"、
  "优先级"能覆盖它。「定时排前面 / 固定排前面」**不是**覆盖规则, 而是
  **一次性改写 `run_list` 顺序的动作**（§2.3）; 动作做完, 命题 2 依然成立。

## 1. 实体层（原子）

一切数据都拆成**有身份、可独立增删改**的**原子实体**。

### 1.1 `Window` —— 一段开放时段（原子）

```python
@dataclass(frozen=True)
class Window:
    id: str                  # ★ 稳定身份（不是位置）—— 见 §1.5
    enabled: bool = True
    period: WindowPeriod     # DAILY / WEEKLY / MONTHLY
    start: time              # 起（时:分）
    end: time                # 止（时:分）—— 可跨午夜（end < start）
    days: tuple = ()         # period=WEEKLY 时的周几（0=周一）；空 = 由 days_from_config 决定
    days_of_month: tuple = ()# period=MONTHLY 时的几号；空 = 整月
    days_from_config: tuple = ()   # 运行时从**任务配置**读星期（见 §1.4）
    times_from_config: tuple = ()  # 运行时从**任务配置**读时刻
```

**语义（不变量）**
* `W1` 一个任务的**可跑集合** = **其所有 `enabled` 窗口的并集**（逐段取或）。
* `W2` **两端同周期** —— `period` 只一份，`start`/`end` 共用（用户裁定 (B)）。
* `W3` 窗口**只回答"可不可以"**，**不回答"几次"**。
  "一天跑两次" = **两个窗口**（不是 `window_slots`，**已废弃**）。
* `W4` `days` / `days_of_month` 为空 + `period` 有值 -> 由 `period` **推导**
  （DAILY=全周、WEEKLY=全周、MONTHLY=1..31）。
  三种都"空"且无动态项 -> `enabled=False`（不限时段）。

### 1.2 `QueueEntry` —— 一条队列条目（原子）

```python
@dataclass
class QueueEntry:
    entry_id: str            # ★ C: `20261010T143005-RealmRaid`（可拆可合并，同秒重复加序号）
    kind: EntryKind          # TASK / REST
    task: str = ''           # kind=TASK
    minutes: int = 0         # kind=REST
    group: str = ''          # ★ 派生**标签**（'timed' / 'fixed'）—— 见 §2.2; **永不落盘**
```

**语义（不变量）**
* `E1` **同一任务可以有多条**（用户用重复条目表达"重复跑整个任务"）。
* `E2` `entry_id` **唯一**且**稳定**（拖拽不改变它）。
* `E3` 状态（完成记忆）**按 `entry_id` 记**，不是按任务 —— 所以重复条目**各跑一次**。
* `E4` `group` 是**派生标签** —— 由任务类别推导, 只用于界面**着色 / 分组显示**。
  ★ 它**不参与排序**（S7 删除三模式后没有任何排序读它）,
  且**永不落盘**（`RunEntry.to_dict()` 刻意不序列化它;
  前端若传了它, 后端也在落盘前用权威值覆盖）。

### 1.3 `Task` —— 任务（原子）

任务的**类别**由 `meta.py` 声明，但**最终类别**跟随 `period`（用户裁定）：

```
category_effective =
    TIMED  且 period_effective == NONE  ->  FIXED     # "不限"就不是定时任务
    其它                                 ->  声明的 category
```

**类别全集**：`FIXED` · `TOPPA` · `LIMITED` · `TIMED`
（★ `CHARGE` **删除** —— 用户裁定"去除旧的充能存量说法"）

### 1.4 动态窗口（窗口**引用配置**）

用户裁定："`AvailabilityWindow` 支持动态 days（运行时从配置读）"、
"窗口仍然是唯一排期依据，这个 B 并不冲突"。

`days_from_config` / `times_from_config` 存的是**相对任务**的点分路径，
`Config.resolve_windows()` 运行时读成实际值，与静态值**取并集**。

★ 路径**相对任务**（`guild_banquet_time.day_1`），因为 `_build_windows()` 只拿到
  **任务级**数据。**踩过**：写成绝对路径 -> 永远解析失败（静默）。

### 1.5 「身份，不是位置」原则（原子化的关键）

| 实体 | 身份 | 位置 |
|---|---|---|
| 窗口 | `Window.id` | 列表下标（**可变**） |
| 队列条目 | `entry_id` | 队列位置（**可变**，用户拖） |

★ **一切"增删改"引用身份，不引用位置**。
**踩过的坑**：按**任务名**删队列条目 -> 同名多条**一删全删**（用户报告的 ⑨）。

## 2. 集合层（分类与顺序）

### 2.1 任务的**两个集合**

| 集合 | 定义 | 谁在这里 |
|---|---|---|
| **`queue`（执行队列）** | `queued_commands()` = `run_list` 的任务 **∪** **已启用**的 `auto_queue` 任务 | 只有这里的任务会跑 |
| **`pool`（候选池）** | 已启用、`auto_queue=False`、且**不在** `queue` 里 | 用户可【添加任务】加进队列 |

★ **不变量 `S1`**：`pending ⊆ queue`（**队列是唯一调度依据**）。
★ **不变量 `S2`**：`pending == queue` 剔除 `waiting` 后的**保序子序列**。

**踩过的坑（本轮修复）**：`schedule_rule`【**已废弃**】`=Filter` 时
`_order_by_timed_priority()`【**已删除**】 **只排序、不剔除** -> 队列外 8 个任务照样跑。
**修**：**任何**规则下都先 `_order_by_queue()` 过滤。

### 2.2 `run_list` 的顺序 = **执行顺序本身**（★ S7 重写）

`run_list` 存的是 `QueueEntry` 的**有序列表** —— 这个**顺序**就是执行顺序,
**没有任何东西能覆盖它**（用户 S7 裁定, 见文件头）。

```
run_list = [
  {entry_id:..., task:'Delegation', kind:'task'},   # group='timed'（派生, 不落盘）
  {entry_id:..., task:'RealmRaid',  kind:'task'},   # group='fixed'
  {entry_id:..., task:'RealmRaid',  kind:'task'},   # 重复条目
  {entry_id:..., task:'AreaBoss',   kind:'task'},   # group='fixed'
  {entry_id:..., kind:'rest',       minutes:30},    # ★ 普通条目（见下方「休息的定义」）
]
```

**不变量 `S3`**：`group` **由任务类别推导**，与用户拖拽**无关**：
* `category_effective in (TIMED, LIMITED)` -> `'timed'`
* `category_effective in (FIXED, TOPPA)` -> `'fixed'`

**不变量 `S4`**（★ S7 重写）：**执行顺序 ≡ `run_list` 的物理顺序**。
`group` **不参与排序** —— 它只是给界面着色的**派生标签**（`E4`）。

★ 旧版 `S4` 写的是"段内顺序 = 用户拖拽；**段先后 = 优先模式**" ——
  ★★ **该表述已作废**：那正是用户裁定"太蠢"的东西（"单独的调度优先级"）★★。

### 2.3 ★★★ 排序是**一个动作**, 不是**一个状态**（S7 核心）★★★

用户裁定：

> "固定任务优先和定时任务优先**直接作为一个快捷排序**就好, 而不是定义一些
>  没有意义的不能跨类别拖动以及**单独的调度优先级**。"

**旧模型（已删）**：`priority_mode`（三个值）是一个**常驻状态** —— 一旦设定,
**每次** `build_queue()` 都按它重排, 并且**限制拖动范围**。于是"顺序"有了
**两个**权威（`run_list` 的物理顺序 + 模式）, 两者冲突时用户看到的是"拖了没用"。

**新模型（现行）**：

| 项 | 内容 |
|---|---|
| 状态 | ★ **没有状态** —— `Optimization` 上**没有** `priority_mode` 字段 |
| 动作 | `Config.sort_run_list(by)`, `by ∈ {'timed', 'fixed'}` —— **会写盘** |
| 端点 | `PUT /{script_name}/queue/sort`, body `{"by": "timed"\|"fixed"}` |
| 语义 | 把 `by` 这一类的条目**整体挪到前面**, 另一类挪到后面 |
| 类内次序 | **稳定排序** —— 同类条目之间的相对次序**一个字不变** |
| 结果 | 队列顺序 = 新的 `run_list` 顺序; 用户**可以随意再拖**（跨类别也行）|
| 幂等 | 再点一次同一个按钮 -> 顺序不变 |
| 非法 `by` | 返回 `False` / `{error}`, **不改配置**（不猜、不静默）|

**为什么必须"不留状态"**：一个常驻状态必然**与 `run_list` 竞争**权威 ——
用户拖完之后, 状态会在下一次 `build_queue()` 时**再压回来**。
★ 用户拖的东西**当场消失**, 而他看不到原因。
把它降级成**一次性的集合重排**（"按类别分区, 稳定拼接"）之后,
**顺序只剩一个权威**: `run_list`。

## 3. 排序层（★ S7 重写: 只有一个顺序权威）

### 3.1 集合定义（恒等映射）

设 `Q` = `run_list` 的**有序条目序列**。执行顺序 `order` **就是** `Q` 本身：

```
order     ≡ Q                                   # 恒等映射 —— 不存在第二个"偏序函数"
pending   = filter(in_window ∧ ¬done ∧ ¬cooling, Q)     # S2: 保序子序列
```

★ **`order` 与 `Q` 之间没有任何中间层** —— 这就是为什么它不可能"拖了没用"。
★ 类别（`group`）**不是**一个偏序维度: 它只是 `E4` 的**显示标签**。

### 3.2 「定时排前面」的实际效果（原来是 `TIMED_FIRST` 的语义）

用户当初要的**行为**是：

```
阶段 1: 只跑 timed 类里**当前在窗口内**的条目
        （不在窗口的 -> waiting, 不阻塞阶段 1 的其它任务）
阶段 2: 当阶段 1 **再无可跑**（全部完成 / 全部不在窗口）时, 才跑 fixed 类
```

★ **S7 之后这条行为仍然可得**, 但**获得方式变了**: 点一次
`PUT /{script}/queue/sort` body `{"by":"timed"}` —— 它把 timed 条目**物理挪到
`Q` 的前面**（§2.3）。之后 3.1 的 `order ≡ Q` **自动**给出阶段 1/2 的效果。

★ 实现上**不需要状态机**：`Config.in_window()` 把不在窗口的踢进 `waiting`,
而 `waiting` 里的条目**不占 pending 位** —— 于是 `pending[0]` 会是"下一个可跑的
timed"; **只有当 timed 的可跑项为空时**它才会是 fixed。**这是自动成立的**。

★ **反例（必须避免）**：fixed 条目**不能**因为"timed 在等窗口"而被提前跑 ——
这由 `pending` 的**保序性**（`S2`）保证: fixed 在 `Q` 里排在 timed 之后,
不可能被"跳过"。

### 3.3 ★★★ 拖动**永远自由**（S7: 约束整簇删除）★★★

用户原话："**固定任务优先和定时任务优先以及不能跨类别拖动太蠢了**。
我只需要保持**可以自由拖动/改变执行顺序**就行。"

| 项 | S7 之后 |
|---|---|
| 跨类别拖动 | ★ **允许** —— 后端**不校验、不拒绝** |
| 同类内拖动 | 允许 |
| `group` 是否限制拖动 | ❌ **不参与**（它只是显示标签, 见 `E4`）|
| "拖动被拒"的返回 | ❌ **不存在** —— `drag_blocked` / `drag_within_group_only` **已删** |
| 唯一会被"改动"的拖动 | 把 `rest` 拖到中间 -> **接受**, 但落盘前**挪到最后**（§2.4, 归一化）|

★ **删掉的东西**（逐项见 `deprecated.md` §3.2）: 前端 `dragWithinGroupOnly` /
`dragRejection` 判据 · 后端 `_check_drag_allowed()` / `drag_blocked` ·
`/schema` 的 `drag_within_group_only`。

★ **反向守卫**: `tests/module/server/test_drag_is_free.py`（11 条）——
跨类别拖动**必须被接受**、`rest` 是**挪位不是拒绝**、生产代码里
**不得**出现 `drag_blocked` / `priority_mode`、`_check_drag_allowed` **不得**存在。

⚠ **刻意不留空壳**: `_check_drag_allowed()` 曾被留成"恒返回放行"的空壳,
后来**整函数删除** —— 因为空壳一旦被接回某个分支就会**静默恒放行**
（"看起来在校验、其实没有"）。

### 3.4 ★ 删除"重排函数"

`_order_by_timed_priority()`【**已删除**】（按 `timed_sort_key` 重排）会让
`pending` **不再是队列的保序子序列**（= 用户拖的顺序失效）。

★ **S7 之后没有任何"排序函数"在 `build_queue()` 里跑**：
`Config._tag_and_place_rest(rl)` 只做两件事 —— **打 `group` 标签** +
**把 `rest` 挪到最后**。排序只在用户**点按钮**时发生（§2.3）。
